# Registry status audit (read-only; nothing is applied)

Written 2026-10-30 on `origin/main` d9f2ad6 (branch `registry-audit`). Source: the data-layer report found that a registry row with no explicit status counts as Confirmed, even where the row's own remark says "not DOK-ING-confirmed, treat as an estimate" (the GA-003 air row). The owner's rule is that Confirmed means confirmed by DOK-ING and that confirmed values are never overwritten; a silent default to Confirmed breaks that rule in both directions (false protection, false credibility).

**Nothing is applied.** No registry row, status, default, engine file or existing test was changed. This document and `outputs/registry_audit/registry_status_audit.{md,csv}` (generated by `python scripts/run_registry_status_audit.py`, about 2 s, git-ignored) are a report and a proposal. Every proposal below is for the owner to accept or reject row by row.

Evidence rule used: a row is called DOK-ING-confirmed (E1) only where a DOK-ING document line in this repo states the value, quoted with `file:line`. The only DOK-ING data file in the repo is `data/dokink_rfi_answers.md` (DOK-ING's verbatim answers; `data/rfi_dokink.md` holds only the questions). `data/MSW_Equipment_Datasheets_Interactive.xlsx` is **not** treated as a DOK-ING document: its file properties name the creator `openpyxl` and the last editor Shahab Nooshmand, and `data/equipment_registry.json` is its flattened extract (`python/equipment_registry.py` docstring). `vendor_model` is empty for all 91 items except one "N/A" (SA-005), so no vendor datasheet exists either. Where no DOK-ING line is found the row is "no DOK-ING evidence found", never "Assumed" by the audit's judgment.

## 1. Where the default is applied, and who reads it (A1)

- **The default:** `python/equipment_datasheet.py:512`, `statuses = {r.get("status", STATUS_CONFIRMED) for r in rows}` inside `slot_status()`; the constant is `:432` and the comment that makes it intentional is `:424-431` ("STATUS_CONFIRMED is the default for every parameter row that has no explicit status key").
- **A second copy of the same default** (written by the data-layer task): `python/parameter_table.py:208`, `status = p.get("status", STATUS_CONFIRMED)` for registry rows. It reads the registry the way `slot_status` does so the table agrees with the datasheet view; it is not an independent decision.
- **It is slot-level too.** `slot_status()` calls a whole category slot Confirmed if ANY row in it is Confirmed. With the fills applied as the app does (`apply_estimates(apply_rfi_fills(build_all_datasheets()))`) `summarize()` reports 262 Confirmed, 48 Engineering Estimate and 236 Missing slots of 546; **only 13 of those 262 Confirmed slots contain a row with DOK-ING evidence (E1)**.

Consumers (list only; nothing changed):

| consumer | where | what it does with the default |
|---|---|---|
| `equipment_datasheet.summarize()` | `equipment_datasheet.py:543-545` | counts Confirmed / Estimate / Missing slots |
| app header metrics | `app.py:2061-2070` | shows the "Confirmed" and "Engineering Estimate" slot counts and the caption "Confirmed (real vendor-datasheet or DOK-ING RFI data)" |

**What would change if the default were different (list only):**

1. `slot_status()`: a slot made only of status-less rows would stop being Confirmed (it would become Estimate, or an error if the status were made a required field). The 10 `RFI_FILLS` rows have no status key either and **would flip too unless given an explicit Confirmed** (they are the E1 rows).
2. `summarize()` and the app header: the Confirmed count (262) would fall toward 13 and the Engineering Estimate count (48) would rise by the same amount; the per-slot warning badge would appear on most slots.
3. `parameter_table` / `data_precedence`: the registry rows for GA-001, GA-003, GA-004 would stop being protected Confirmed candidates.
4. **No existing test asserts the Confirmed / Estimate split** (searched `tests/` for `confirmed_category_slots`, `estimated_category_slots`, `slot_status`: no hit). The app's hard-coded count checks use `populated_category_slots` and `total_real_data_points`, which do not move (unless the default became `Missing`, which would also change them).
5. `design_basis`, `uncertainty`, `plant_status`: no change.
