# Design-basis ledger

Generated by `scripts/export_design_basis_ledger.py` (task A3) from `parameter_table.build_ledger()`, `python/ledger_coverage.py` and `data/ledger_exceptions.json`; `tests/test_design_basis_ledger.py` fails if this file or `design_basis_ledger.csv` differs from a fresh generation. Nothing in it is a second copy of a value: each row names where it lives by symbol (`anchor`, never a line number), so it does not go stale when a line is added above a constant.

Statuses are the project's: Confirmed (DOK-ING source cited), Calculated, Estimated, Assumed, Missing, plus Unverified (registry). A row with a registry counterpart takes the status, `origin` and `source_line` the provenance overlay (`data/registry_status_overlay.json`) gives that registry row; any other row is Assumed and says so (`STATUS ASSIGNED BY THIS TABLE`). `origin` is `NOT STATED` where the owner's worksheet has no answer for the row. `consumers` lists the engine keys that really call `get_input` for an engine input (an instrumented run), and the functions that name the constant otherwise (`ast`); `NONE FOUND` is reported, not hidden. `upgrade_question` is empty where the repo holds no question that would upgrade the row; no question was invented.

### FE-001 default delivery rate against FE-003 nominal feed rate

Engine: `FE001_DEFAULT_DELIVERY_RATE_KG_H` = 41.67 kg/h, the default of the engine input `FE-001-INPUT/msw_delivery_rate_kg_h` (the rate at which MSW arrives in the hopper; a scenario knob). Registry: FE-003 'Nominal feed rate' = 0.042 t/h (remark: "Matches DOK-ING's 1 tpd (41.7 kg/h) nominal basis directly"), Confirmed by the owner's worksheet with the DOK-ING line `data/dokink_rfi_answers.md:11` (RFI answer 1: 'Nominal capacity fixed at 1 tonne/day (1,000 kg/day) for continuous 24/7 operation'). They are not one quantity in one basis that differ by a unit conversion: (1) the registry row is the rate at which the plant FEEDS the process, the engine value is the rate at which feed is DELIVERED to the hopper (the hopper level changes by delivery minus feed, `fe001_inventory`); DOK-ING's answer is the processing capacity and says nothing about deliveries; (2) the basis of the 1,000 kg/day (as received or dry) is not stated in DOK-ING's line and is an open question (`docs/master_open_questions.md` Section 1 item 2) while the code comment says AS-RECEIVED. The row stays Assumed.

### GA-002 typical pressure

Engine: `GA002_TYPICAL_PRESSURE_MBAR_G` = 100.0 mbar(g), the typical gasifier pressure used by the suction cross-check of GC-014. Registry rows of the gasifier vessel: GA-001 'Design pressure' 500 mbar(g) (a design quantity); GA-001 'Operating pressure (typical)' 100 mbar(g) (remark: 'Matches ~1.1 bar absolute already used in the pressure profile chart'); GA-002 'Design pressure' 500 mbar(g) ('Matches GA-001's design pressure directly'); GA-002 'Operating pressure range' 50-150 mbar(g) ('Band around the 100 mbar(g) typical value'). Design pressure and typical or operating pressure are different quantities and nothing is borrowed across them. The only row that is the same quantity (typical operating gauge pressure of the gasifier vessel, mbar(g), same value) is GA-001 'Operating pressure (typical)'; GA-002's own row is a band, not a typical value. So `GA-002.typical_pressure_mbar_g` borrows from GA-001 'Operating pressure (typical)' (Unverified (registry)); `ledger_rows.quantity_class` and a test refuse any borrowing across a design row and a typical or operating row.
