# Maturity classes and readiness gates for the AI / optimisation / virtual-sensing modules

Task A10, branch `maturity-gates`. Additive: no model result, default, Confirmed value, registry value or persisted key changed (every persisted entry equals the unmodified `origin/main` snapshot in both
`tail_gas_mode`s). Nothing here says anything about DOK-ING's plant: no plant data exists in this project, so every module's `evidence` is `None`.

## 1. The classes (`python/maturity.py`)

Lowest first; a module that fits two classes takes the lower.

| class | meaning | modules today |
|---|---|---|
| `ILLUSTRATION` | demonstrates a method on hypothetical plants or invented data | federated_learning, multi_agent_negotiation, multi_module_orchestration, sim_to_real |
| `RULE_BASED` | fixed rules or thresholds, no fitting | copilot, predictive_maintenance, root_cause, safety_flags, regulatory_drafting, novelty_audit, sa_virtual_sensors, ai_automation_layer, operator_setpoints |
| `PHYSICS_ESTIMATE` | a calculation from the twin's own steady-state physics with Assumed / Estimated inputs; no plant data | optimizer, performance_guarantee, uncertainty |
| `SYNTHETIC_BENCHMARK` | trained or tested only on data generated by the twin | pinn_kinetics, time_series_sim, tda_analysis |
| `TRAINED_ON_PLANT_DATA` | fitted to Measured plant data | none |
| `VALIDATED_ON_HELDOUT` | shown against held-out plant data under the readiness gates | none |

## 4. The gate (`python/readiness_gate.py`)

`readiness_gate(capability, evidence, criteria)` returns `{"passes", "reasons", "maturity_allowed"}`. **Every numeric criterion defaults to `None`** ("criteria not yet set — to be fixed with literature
task C6 and DOK-ING"); with one `None` the gate fails with `criteria not set: <field>`. No number for data volume, coverage or error is written anywhere.

| capability | required evidence items |
|---|---|
| calibration | measured_pairs_count, operating_range_coverage, instrument_uncertainty_known, identifiability_screen_passed |
| validation | calibration items + heldout_campaigns, heldout_error |
| virtual_sensing | the validation items |
| predictive_maintenance | the validation items + failure_events_count |
| optimisation | the validation items + confirmed_envelope_present |
| online_replacement | the validation items + confirmed_envelope_present, fallback_defined |

Criteria fields: `min_measured_pairs`, `min_operating_range_coverage`, `min_heldout_campaigns`, `max_heldout_error`, `min_failure_events`. `maturity_allowed`: no evidence → `PHYSICS_ESTIMATE`;
twin-generated data only → `SYNTHETIC_BENCHMARK`; Measured plant data → `TRAINED_ON_PLANT_DATA`; plant data whose held-out campaigns meet both held-out criteria → `VALIDATED_ON_HELDOUT`.

**NOT VERIFIED:** the roadmap's section 7 table is not in this repository. The item names are the ones the task names; the assignment to capabilities follows one stated rule (each capability adds its own
item to the validation set). The owner should correct `REQUIRED` against the roadmap; the tests pin the current version.

## 5. What the gate does not do

It is informational: nothing in the engine, the runtime or the UI reads it, and it changes no value. It does not check that evidence is genuine (a count is a count), does not set any threshold, does not
promote a module (the registry class is a declaration that a person changes with evidence), and is not wired into the runtime. It says what is missing, not that something is good.

## 6. What would move each module up (evidence, not code)

* **ILLUSTRATION → anything higher** needs the thing the module imagines: federated_learning and multi_agent_negotiation a real second plant's data; multi_module_orchestration real parallel trains;
  sim_to_real Measured pairs from a real instrument with a known uncertainty.
* **predictive_maintenance (RULE_BASED)** would need Measured conversions with known instrument uncertainty and recorded degradation / failure events (`predictive_maintenance` capability) before its thresholds could be fitted
  instead of chosen.
* **RULE_BASED** modules are not data-driven; they stay RULE_BASED. copilot, root_cause, safety_flags, regulatory_drafting and novelty_audit would change class only if rewritten as fitted methods.
  sa_virtual_sensors would become a measurement-backed virtual sensor only with `calibration` and `virtual_sensing` evidence (measured pairs across the operating range, instrument uncertainty,
  identifiability, held-out campaigns).
* **PHYSICS_ESTIMATE → TRAINED_ON_PLANT_DATA**: Measured plant data with known instrument uncertainty over the operating range (`calibration`). The optimizer additionally needs a DOK-ING-confirmed envelope and a fallback (`optimisation`, `online_replacement`); uncertainty and performance_guarantee would take
  measured distributions in place of the Assumed ranges.
* **SYNTHETIC_BENCHMARK → TRAINED_ON_PLANT_DATA**: replace the twin-generated training or test data by Measured plant data; pinn_kinetics also needs the held-out campaigns for `validation`.
* **→ VALIDATED_ON_HELDOUT** needs held-out campaigns whose error meets the criteria once they are set.

## 7. The synthetic benchmark (`scripts/run_synthetic_benchmark.py`)

Only predictive_maintenance: the twin's HTS conversion with a known activity factor falling 1.00 → 0.60, Gaussian noise on the conversion at 0 / 0.2 / 0.5 / 1 / 2 percentage points, five seeds, the
inverse-kinetics method. **It measures the code, not any plant**; the noise levels are test inputs, not instrument specifications. Zero noise recovers the truth to 5e-10; 1 percentage point of noise gives a
mean absolute activity error of about 0.018 (bias about −0.001). The other 18 modules are listed with the reason there is no benchmark yet. Output: `outputs/benchmark/synthetic_benchmark.md` and `.csv` (git-ignored).
